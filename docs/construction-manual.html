0开工前须知

先读这一页，能省掉后面一半的返工。

这份手册怎么用

全篇按施工顺序排列，每一步都是「命令 → 预期输出 → 记录什么」的三段式。带 预期 的框是判断这一步是否真的成功的依据——看不到对应输出就不要往下走，否则错误会累积到很远的地方才爆出来。

两条线是独立的

Cosmos 线和 EVM 线之间没有任何代码依赖，可以分两天做，也可以两个终端并行。唯一的交集是根目录的 make check。

一句话说清"挖矿"

⚠ 术语校正

Cosmos 用的是 PoS：验证者质押 uedu → 参与共识出块 → 验证者和委托人按比例分奖励。整个流程里没有算力、没有难度、没有 nonce 爆破。作业报告里写"挖矿"时必须加这句限定，否则概念是错的。

1环境准备

目标：四条 version 命令全部有输出。

1.1 基础工具链

node -v         # 需要 v20 或更高

macOS 缺什么就补什么：

Go 环境变量

确认 go env GOPATH 下的 bin 在 PATH 里，否则 make install 装出来的 edud 找不到：

echo 'export PATH="$PATH:$(go env GOPATH)/bin"' >> ~/.zshrc
source ~/.zshrc

1.2 安装 Ignite CLI v29

Cosmos 线用 Ignite 起链。先试官方安装脚本：

curl https://get.ignite.com/cli! | bash
ignite version
预期 输出包含 Ignite CLI version: v29.x。
✗ 不要用 go install 装 Ignite

本项目搭建时踩过：go install github.com/ignite/cli/v29@v29.8.0 会失败（该路径不是 main 包），…/v29/ignite@v29.8.0 也不存在。就算写对入口 …/v29/ignite/cmd/ignite@v29.8.0，当前 Go 也会因为该模块含 replace 指令而直接拒绝安装。这不是你的环境问题，是 Go 的规则。

官方脚本失败时的备用方案（从源码构建）

git clone --depth 1 -b v29.8.0 https://github.com/ignite/cli.git /tmp/ignite-src
cd /tmp/ignite-src
go build -o "$(go env GOPATH)/bin/ignite" ./ignite/cmd/ignite
ignite version
⚠ 首次构建会很慢

它要拉整套 Cosmos SDK 依赖，5–15 分钟没有任何输出是正常的，不要 Ctrl-C。如果 Ignite 因为加载本机已装插件而报错，加一个干净的配置目录再跑：IGNT_CONFIG_DIR=/tmp/ignite-config ignite …。

2作业一：Cosmos 自己的链

钱包分发 → 转账 → 质押出块拿奖励。链名 edu，二进制 edud，地址前缀 edu，denom uedu。

ignite chain serve→Genesis 分发→查地址余额→bank send→staking delegate→distribution rewards

2.1 起链（终端 A，全程保持运行）

cd cosmos-chain
ignite chain serve

这条命令一次干了四件事：编译 edud → 按 config.yml 生成 Genesis → 创建 alice/bob/validator 三个密钥 → 启动节点开始出块。

预期 终端持续滚动 INF committed state ... height=1,2,3，并打印出 Token faucet: http://0.0.0.0:4500。看到高度在涨 = 链活着。
⚠ 关于重置

ignite chain serve 默认复用已有本地数据。要从干净 Genesis 重来才加 -r（ignite chain serve -r）——这会删掉之前的余额和交易记录，做完转账演示前别乱加。

安装 edud 命令（终端 B）

cd cosmos-chain
make install          # 装到 $(go env GOPATH)/bin/edud
edud version --long

不想装全局也行，用仓库里已构建的二进制：make build 后以 ./build/edud 替换下文所有 edud。

2.2 钱包分发与余额

分发逻辑写在 config.yml，链一初始化就生效：

账户Genesis 余额角色
alice300000000uedu普通用户 · 转账发起方
bob200000000uedu普通用户 · 收款方 + faucet 出款账户
validator1000000000uedu验证者，其中 500000000uedu 已绑定为初始质押
 
edud keys list --keyring-backend test

ALICE=$(edud keys show alice -a --keyring-backend test)
BOB=$(edud keys show bob   -a --keyring-backend test)
echo "$ALICE"; echo "$BOB"

edud query bank balances "$ALICE"
edud query bank balances "$BOB"
预期 地址形如 edu1xxxxxxxx…；余额分别是 300000000uedu 与 200000000uedu。
🔒 只记录地址

keys list 和 keys show 只输出公开地址。永远不要执行 keys export / keys mnemonic 并把结果贴进作业报告或仓库。

Faucet（可选）

Ignite 起链时会同时开一个 faucet 服务（默认 :4500），从 bob 账户出款，单地址每 24 小时上限 10000000uedu。演示"给新钱包发币"时用它：

edud keys add carol --keyring-backend test          # 新建一个空钱包
CAROL=$(edud keys show carol -a --keyring-backend test)

curl -X POST http://0.0.0.0:4500 \
  -H "Content-Type: application/json" \
  -d "{\"address\":\"$CAROL\",\"coins\":[\"1000000uedu\"]}"

edud query bank balances "$CAROL"

2.3 Bank 转账

edud tx bank send "$ALICE" "$BOB" 100000uedu \
  --from alice \
  --keyring-backend test \
  --chain-id edu \
  --yes
预期 返回 JSON 里 code: 0 和一个 txhash。code 非 0 就是失败，看 raw_log。

等一两个区块后核对——这是验收要的"余额变化"证据：

edud query tx <txhash>
edud query bank balances "$ALICE"   # 少 100000uedu + 手续费
edud query bank balances "$BOB"     # 多 100000uedu

2.4 质押、出块与奖励（作业里的"挖矿"）

质押要用 eduvaloper… 格式的 operator 地址，和普通 edu1… 地址不是一个东西：

VALOPER=$(edud keys show validator -a --bech val --keyring-backend test)
echo "$VALOPER"                      # eduvaloper1…

edud query staking validator "$VALOPER"
预期 看到 status: BOND_STATUS_BONDED、tokens: 500000000、以及佣金率 commission。

用 alice 委托，然后查奖励：

edud tx staking delegate "$VALOPER" 100000uedu \
  --from alice --keyring-backend test --chain-id edu --yes

edud query staking delegations "$ALICE"
edud query distribution rewards "$ALICE"      # 等几个区块才有数
edud query distribution commission "$VALOPER" # 验证者佣金收入
报告里要讲清的因果链

验证者质押 uedu → 按质押权重轮流提议区块 → 区块被 CometBFT 共识确认 → 区块奖励进入 distribution 模块 → 验证者抽佣金，剩下按委托比例分给委托人。奖励来自出块，不来自算力。

最后领取奖励，闭环这条线：

edud tx distribution withdraw-rewards "$VALOPER" \
  --from alice --keyring-backend test --chain-id edu --yes

edud query bank balances "$ALICE"   # 余额里多出奖励部分

2.5 一键演示脚本

答辩/录屏时用它，比手敲一串命令稳。默认只读，不会动链上状态：

./scripts/demo.sh                                    # 只查 keys / 高度 / 余额
DEMO_SEND=1 ./scripts/demo.sh                        # 额外发一笔转账
VALIDATOR_ADDRESS="$VALOPER" DEMO_DELEGATE=1 ./scripts/demo.sh   # 额外发一笔委托

没装全局 edud 时指定二进制：EDUD_BIN=./build/edud ./scripts/demo.sh。

✓ 作业一收工标准

手上有：三个账户地址、Genesis 余额截图、转账 txhash + 前后余额、validator 状态、delegation 记录、rewards 查询结果，以及一句"这是 PoS 不是 PoW"的说明。

关于 npm audit 告警

Hardhat 2 和 The Graph CLI 的开发依赖会报一批非 critical 告警，不要执行 npm audit fix --force——它会把 Hardhat 升到 3，直接破坏本项目。（subgraph/package.json 里已用 overrides 把有 Zip Slip 漏洞的 decompress 换成 @xhmikosr/decompress@11.1.3，那个 critical 已经处理掉了。）

3.2 本地节点与部署（两个终端）

终端 A —— 起一个持久节点，别关：

npm run node
预期 打印 Started HTTP and WebSocket JSON-RPC server at http://127.0.0.1:8545/ 和 20 个测试账户。

终端 B —— 部署：

npm run deploy:local
预期 EventStore deployed to: 0x5FbDB2315678afecb367f032d93F642f64180aa3（干净节点上的首个部署地址通常就是这个）。
✗ 别用 --network hardhat

--network hardhat 起的是随进程消失的一次性内存链：部署脚本一结束，合约就没了，随后任何读取都会返回空。必须用上面这种「终端 A 常驻 + 终端 B --network localhost」的组合。

把地址写进 .env：

FROM_BLOCK=1
DATA_KEY=course
DATA_VALUE=hello
.env

3.3 用 ethers.js 读普通 RPC

npm run read:rpc
预期 { chainId: '31337', blockNumber: 1, blockHash: '0x…', transactionCount: 1 }。

这一步对应作业里的"一般 RPC 节点"：new ethers.JsonRpcProvider(url) 之后，getNetwork / getBlockNumber / getBlock 三个调用就够说明问题。换任何兼容 EVM 的 RPC 只需改 RPC_URL。

3.4 写事件，再用三种方式读回来

合约不存 storage，只发日志——这正是作业要的"通过日志形式写链上数据"：

event DataWritten(
    address indexed writer,
    bytes32 indexed keyHash,
    string key,
    string value,
    uint256 timestamp
);
EventStore.sol 
npm run write:local
npm run read:events
预期 write:local 打印 writer / transaction / block；read:events 依次输出三段：provider.getLogs、queryFilter、transaction receipt，三段里的 key、value、writer 完全一致。
读法层级用来说明什么
provider.getLogsJSON-RPC 原生日志本质是 topics + data，需要自己按 ABI 解码
contract.queryFilterethers.js 封装ethers 帮你编码过滤条件并解码成命名参数
getTransactionReceipt交易维度日志是交易执行的副产物，挂在 Receipt 上
indexed 的作用

writer 和 keyHash 带 indexed，会进 topics 从而可被过滤；key/value/timestamp 在 data 里，只能读出来不能当过滤条件。这也是 keyHash 存 keccak256(key) 的原因——字符串没法直接做 indexed 精确匹配。

4.2 申请 Infura 与 Alchemy 的 RPC

作业要求"分别用 Infura 和 Alchemy 读链上数据"，所以两个都要申请：

服务拿到的东西URL 形态
InfuraAPI Keyhttps://sepolia.infura.io/v3/<KEY>

SEPOLIA_RPC_URL=https://sepolia.infura.io/v3/<你的KEY>
INFURA_SEPOLIA_RPC_URL=https://sepolia.infura.io/v3/<你的KEY>

4.4 Infura vs Alchemy 对比

npm run compare:providers
预期 两行输出 Infura: chainId=11155111 block=… / Alchemy: chainId=11155111 block=…，chainId 相同、区块高度相差 0–2 块。

5作业二 C：The Graph 把数据读回来

对应 README 里最后一个 ⏳。前提：4.3 已经拿到真实合约地址和部署区块。

subgraph/subgraph.yaml

其余字段不用动：network: sepolia 已对，事件签名 DataWritten(indexed address,indexed bytes32,string,string,uint256) 与合约完全匹配。

npm run graph:codegen

5.4 GraphQL 查询（作业的最终产出）

在 Studio 的 Playground 里直接粘贴 subgraph/queries/data-written.graphql 的内容：

query RecentDataWritten {
  dataWrittens(first: 20, orderBy: timestamp, orderDirection: desc) {
    id writer keyHash key value timestamp blockNumber transactionHash
  }
}
预期 返回你在 4.3 写入的那条记录，key/value/writer 与 Etherscan 上的日志一致。截这张图，它就是"用 The Graph 把数据读回来"的证据。

也可以用 curl 打查询端点，作为脚本化证据：

curl -X POST <Studio 给的 Query URL> \
  -H "Content-Type: application/json" \
  -d '{"query":"{ dataWrittens(first:5,orderBy:timestamp,orderDirection:desc){ key value writer blockNumber } }"}'
报告里要答的那道题：RPC 直查 vs The Graph
ethers / getLogsThe Graph
数据来源节点实时扫描区块预先索引好的数据库
查询能力只能按 topics 过滤任意字段排序、分页、条件组合
历史范围受 RPC 区块跨度限制从 startBlock 起全量
成本范围一大就慢/被限流查询快，但要先同步索引
实时性最新块立即可读落后若干区块

7踩坑速查表

前六条是这个项目搭建时真实遇到并修掉的，不是假想。

现象原因与解法
go install …/ignite@v29.8.0 报 module … found, but does not contain package 包路径错。真实入口是 ignite/cmd/ignite；但即使写对，Go 也会因该模块含 replace 指令拒绝 install。改用官方脚本或源码 go build（见 1.2）。
Ignite 命令启动时报插件/apps 相关错误 本机 ~/.ignite 里的旧插件被加载。用干净配置目录：IGNT_CONFIG_DIR=/tmp/ignite-config ignite …
go mod tidy 卡住十几分钟不动 Ignite 生成的 go.mod 里 tool 区块会把 buf、protoc 插件、lint 工具全拉一遍，与跑链无关。直接 make build（只解析节点二进制真正需要的依赖）即可生成 go.sum。
go build 报 "fmt" imported and not used 之类 scaffold 中途被打断留下的残留 import。删掉那几行再 gofmt -w 即可，不是逻辑问题。
Go 命令报缓存目录权限错误 换一个可写缓存目录：GOCACHE=/tmp/bh-go-cache go test ./...
npm audit 报 critical decompress Zip Slip 已通过 subgraph/package.json 的 overrides 换成 @xhmikosr/decompress@11.1.3。别用 audit fix --force，它会把 Hardhat 升到 3。
部署成功但读不到任何日志 八成用了 --network hardhat（一次性内存链）。改成终端 A npm run node + 终端 B deploy:local。
Network sepolia doesn't exist SEPOLIA_RPC_URL 与 DEPLOYER_PRIVATE_KEY 必须同时存在才会注册该网络。检查 .env 位置与拼写。
读事件超时 / RPC 报 block range 超限 FROM_BLOCK 没设，从创世块扫了。设成合约部署区块号。
Subgraph 一直 Syncing 且 0 条数据 subgraph.yaml 的 address 还是全零，或 startBlock 晚于实际写入区块。改完重新 codegen → build → deploy。
graph deploy 报找不到 subgraph Studio 上的名字与 --studio event-store 不一致，或没先跑 graph auth。
Cosmos 转账返回 account sequence mismatch 同一账户连发交易太快。等一个区块再发，或加 --sequence 指定。

8安全红线

违反任意一条，作业分数事小，钱包被清空事大。

  • 私钥 / 助记词 / API Key / Deploy Key 只存在于本地 .env，该文件已在 .gitignore 中；提交前用 git status 确认它没被跟踪。
  • 测试网钱包与真实资产钱包完全隔离，两者不共用助记词。
  • 作业报告和截图里只出现公开信息：地址、txhash、区块号、合约地址、浏览器链接。
  • Cosmos 侧只用 --keyring-backend test（明文存储，仅限本地学习），不要在这个 keyring 里放任何有价值的密钥。
  • 没有链上证据（地址 + txhash + 区块号 + 浏览器链接）之前，报告里不能写"已部署"。
  • 不要为了消除依赖告警执行破坏性升级；当前 critical 已处理，其余是开发工具链的已知噪音。
